# Community Validation of Five Homegrown Book-Pipeline Practices

Research date: 2026-08-31. Method: WebSearch + direct WebFetch of each repo's GitHub page. Every star count below was read from the live GitHub page at fetch time; anything not directly loaded is marked **[unverified]**. No official Anthropic skill covers any of these five practices — `anthropics/skills` ships docx/pdf/pptx/mcp-builder/skill-creator etc., nothing for reproducible manuscripts or book review ([repo](https://github.com/anthropics/skills)).

---

## Practice 1 — Executable chapters (code-generated tables/figures + pytest pinning printed numbers)

**Homegrown:** every table/figure generated by a Python module beside the chapter; a pytest suite pins the printed numbers so prose can't drift from code.

| Candidate | URL | Adoption evidence (verified) | Covers | Misses |
|---|---|---|---|---|
| Quarto computed books | github.com/quarto-dev/quarto-cli | 6.0k stars, 456 forks, maintained by quarto-dev (Posit) org | Executed code chunks per chapter; `freeze` caches results; inline computed values (`` `r ...` ``/`{python}`) so numbers are *inserted*, never typed — structurally cannot drift | Requires .qmd source + Quarto toolchain; no test suite — drift prevention is by construction, not assertion |
| Jupyter Book 2 / MyST-MD | executablebooks.org; SciPy 2025 proceedings paper (doi 10.25080/hwcj9957) | Jupyter sub-project; powers The Turing Way, QuantEcon, Project Pythia, QIIME 2 docs; SciPy proceedings built on MyST | Executable notebook chapters, cached execution | Same: no assertion layer; notebook-based |
| nbval (pytest plugin) | github.com/computationalmodelling/nbval (docs: nbval.readthedocs.io; paper arXiv:2001.04808) | pytest plugin with a published paper; long-standing (docs at v0.11.0) — star count not loaded **[unverified]** | Exactly the homegrown idea: re-executes cells and asserts recomputed output == stored output; sanitizer regexes for nondeterminism | Notebook-only; doesn't cover prose statements about the numbers |
| pytest `--doctest-modules` | docs.pytest.org (built into pytest) | Core pytest feature, universally available | Pins printed numbers in docstrings/examples | Doesn't reach into markdown prose either |
| Claude skill: `/audit-reproducibility` (pedrohcgs/claude-code-my-workflow) | github.com/pedrohcgs/claude-code-my-workflow | 1.5k stars, 3.0k forks, MIT, active 2026-08-24, maintained by Pedro Sant'Anna (Baylor econometrician) | Cross-checks paper ↔ code numeric claims with tolerance thresholds; v1.9 `passport.yaml` tracks each claim as PASS/FAIL/STALE/UNVERIFIED | It audits after the fact; doesn't generate the artifacts |

**Verdict: KEEP homegrown core, HYBRID the audit layer.** The community's gold standard ("never hand-type a number" — knitr/Quarto inline computation, r4ds ch. 28) prevents drift *by construction*, which is stronger than pinning — but only inside .qmd/notebook toolchains. For a markdown-prose book, the homegrown module+pytest design is the same architecture nbval formalized (re-run, compare printed output), so it is community-validated in pattern if not in artifact. Adopt the `passport.yaml` per-claim PASS/FAIL/STALE ledger idea from claude-code-my-workflow to extend pinning from tables into prose claims.

## Practice 2 — syllabus.yaml as the canonical structure file

**Homegrown:** one YAML (modules → chapters, order, status) that every phase reads; builds and cross-refs derive from it.

| Candidate | URL | Adoption evidence (verified) | Covers | Misses |
|---|---|---|---|---|
| Quarto `_quarto.yml` book projects | quarto.org/docs/books/ | quarto-cli 6.0k stars; the default for computational books | Canonical ordered chapter list; build + cross-refs + numbering derive from it | No per-chapter workflow *status* field; assumes Quarto renderer |
| Jupyter Book 2 `myst.yml` | executablebooks.org | JB2 is a Jupyter sub-project; replaces `_config.yml`+`_toc.yml` | Same canonical-TOC role | Same — no status tracking |
| mdBook `SUMMARY.md` | github.com/rust-lang/mdBook | 22.1k stars, 1.9k forks, maintained by rust-lang org, 3,262 commits | Canonical structure file drives the whole build | Markdown-list format, less machine-friendly than YAML; HTML-docs oriented, weak print story |

**Verdict: pattern ADOPTED by the community everywhere; artifact KEEP (or migrate as a side effect).** "One canonical structure file that everything derives from" is exactly how all three major book systems work — the homegrown practice is a reimplementation, not an invention. The only bespoke part is the `status:` field (drafting-workflow state), which none of the standard configs carry. If the pipeline ever moves to Quarto (see Practice 3), `_quarto.yml` absorbs the TOC role and `status` moves to a small sidecar file. Until then, syllabus.yaml is fine; it is not the risky part of the stack.

## Practice 3 — Homemade render pipeline (markdown → styled HTML → headless-Chromium PDF → pypdf metadata)

**Homegrown:** node script for HTML, Playwright/Chromium print-to-PDF, pypdf for bookmarks/metadata.

| Candidate | URL | Adoption evidence (verified) | Covers | Misses |
|---|---|---|---|---|
| Paged.js + pagedjs-cli | pagedjs.org; github.com/pagedjs/pagedjs | Coko Foundation lineage (Adam Hyde); pagedjs-cli is literally HTML → Puppeteer headless-Chromium → PDF; used in Editoria book production; W3C CSS print workshop position paper | The *same architecture* as the homegrown pipeline, plus real paged-media CSS: running headers, page numbers, footnotes, page floats | Star counts not loaded (repo is mirrored from Coko GitLab) **[unverified]**; cli at v0.4.x — youngish versioning |
| Vivliostyle | github.com/vivliostyle/vivliostyle.js | 782 stars, 5,342 commits, 30+ contributors, Vivliostyle org (Japan); used by Fidus Writer ≥3.5 for PDF | CSS typesetting engine for HTML→PDF books; CLI + viewer | Smaller Western community |
| WeasyPrint | github.com/Kozea/WeasyPrint | 9.5k stars, 865 forks, Kozea + CourtBouillon commercial support | Python HTML+CSS→PDF, no browser needed; strong paged-media support | Its own renderer ≠ Chromium: your screen CSS may render differently |
| O'Reilly Atlas (proof the path is respected) | docs.atlas.oreilly.com | O'Reilly's own production system: HTMLBook + CSS themes → print-ready PDF; 3,000+ books over 8+ years | Existence proof that HTML+CSS→PDF is a professional print path, not a hack | Proprietary; not adoptable directly |
| Quarto render / Pandoc→LaTeX | quarto.org | 6.0k stars; the mainstream one-tool replacement | Markdown→PDF (via LaTeX or Typst) + EPUB + HTML from one source | Different typography model; restyling means leaving your CSS |
| Typst | typst — see underleaf.ai/blog/typst-vs-latex; Wikipedia | Fast-rising, but as of 2026 only a couple of journals accept it; institutional adoption still behind LaTeX | Modern fast PDF typesetting | Not an HTML path; ecosystem still maturing for print books |
| pypdf (metadata/bookmarks step) | github.com/py-pdf/pypdf | Standard Python PDF library **[stars unverified]** | Exactly its intended use | — |

**Verdict: HYBRID.** HTML-print-via-Chromium is a *respected, production-proven* path (O'Reilly Atlas 3,000+ books on HTML+CSS; pagedjs-cli ships the identical Chromium architecture; Fidus Writer/Editoria use Vivliostyle). The homegrown pipeline's risk is not the architecture but the bespoke pagination logic — running headers, page breaks, TOC page numbers are the hard 20% that Paged.js/Vivliostyle spent years on. Recommendation: keep md→HTML→Chromium→pypdf, but layer Paged.js (or Vivliostyle CLI) into the HTML stage instead of hand-rolled print CSS hacks; evaluate Quarto only if you also want EPUB/LaTeX outputs from the same source.

## Practice 4 — Verify-then-edit review (re-run shipped code before editing either side)

**Homegrown:** when prose contradicts a printed number, re-run the module to decide which side is wrong.

| Candidate | URL | Adoption evidence (verified) | Covers | Misses |
|---|---|---|---|---|
| ACM Artifact Evaluation / badging | e.g. 2024.acmmmsys.org reproducibility; ctuning/artifact-evaluation | Formal conference institution: "Results Reproduced" badge = independent re-execution of artifacts confirms the paper's numbers | The named community practice: claims are settled by re-running the artifact, not by eyeballing | Conference process, not tooling you install |
| MixtapeTools `referee2` protocol | github.com/scunning1975/MixtapeTools | Scott Cunningham (Baylor, author of *Causal Inference: The Mixtape*); 5-audit protocol; verifies tables/figures are programmatically generated; cross-language replication to 6+ decimals | Codified verify-before-trust for empirical manuscripts, packaged as a Claude skill/persona | Econ-flavored; stars not loaded **[unverified]** |
| `/audit-reproducibility` + passport.yaml (claude-code-my-workflow) | github.com/pedrohcgs/claude-code-my-workflow | 1.5k stars / 3.0k forks, active Aug 2026 | Per-claim provenance ledger (PASS/FAIL/STALE/UNVERIFIED) — the productized form of verify-then-edit | — |
| lcrawfurd/claude-skills `referee2` | github.com/lcrawfurd/claude-skills | 8 stars — small, but implements the Cunningham protocol as 5 parallel audits | Same idea, portable slash-command form | Tiny adoption |

**Verdict: KEEP — the homegrown practice IS the community practice.** "Re-run the code to decide which side is wrong" is exactly what artifact evaluation's *Results Reproduced* badge institutionalizes, and at least two independent academic Claude-skill authors (Sant'Anna, Cunningham) have codified it for AI-assisted workflows. Upgrade path: adopt the passport.yaml claim-status ledger so verification outcomes persist across review rounds instead of being re-litigated.

## Practice 5 — Chapter-sharded parallel agent review (one agent per chapter-pair, file reports, compile after)

| Candidate | URL | Adoption evidence (verified) | Covers | Misses |
|---|---|---|---|---|
| pedrohcgs/claude-code-my-workflow | github.com/pedrohcgs/claude-code-my-workflow | 1.5k stars, 3.0k forks; 18 specialized reviewers; "orchestrator runtime" = parallel agents + reduction over shared schemas + iterate-to-convergence | Fan-out/compile pattern at real adoption scale | Shards by *concern* (proofreader, claim-verifier, methods-referee), not by chapter |
| claesbackman/AI-research-feedback | github.com/claesbackman/AI-research-feedback | 474 stars, 83 forks; 8 parallel review agents incl. advocate-vs-skeptic pair; consolidated dated report in `reviews/` | Parallel review + structured consolidation, incl. adversarial pairing | Paper-scale, single consolidated report (no per-shard files); shards by dimension |
| andrehuang/academic-writing-agents | github.com/andrehuang/academic-writing-agents | 177 stars, 18 forks; 12 agents (5 review, orchestrator synthesizes Critical/Important/Minor); review-then-act separation | Parallel specialists + prioritized synthesis + diagnose-before-fix | Same: dimension-sharded, not chapter-sharded |
| lcrawfurd `openaireview` | github.com/lcrawfurd/claude-skills | 8 stars; "parallel sub-agent section analysis" | The closest to *section*-sharding | Negligible adoption |

**Verdict: KEEP, pattern validated.** Fan-out-parallel-agents-then-compile is now the standard shape of AI manuscript review (three independent repos, 177–1.5k stars, all 2025–2026-active). Nobody with adoption shards by chapter specifically — they shard by review dimension — but chapter-sharding is the correct adaptation when the unit is a 14-chapter book that exceeds one context window; the two axes compose (per-chapter fan-out × per-dimension checklists). Worth stealing: the advocate/skeptic adversarial pair (Bäckman) and severity-tiered synthesis (Huang).

## Overall recommendation, ranked by risk reduction

1. **Practice 3 (render pipeline) — biggest de-risking opportunity.** The architecture is community-proven (O'Reilly Atlas, pagedjs-cli), but the bespoke print-CSS/pagination code is where a homegrown pipeline silently produces bad books. Layer **Paged.js** into the existing Chromium step (drop-in: it's the same Chromium architecture) rather than rewriting; consider Quarto only for a multi-format future.
2. **Practice 1 (executable chapters) — HYBRID.** The design is sound (it's the nbval pattern). Adopt the **passport.yaml claim-ledger** idea to cover numeric claims in prose, which pytest pinning of tables alone misses.
3. **Practice 4 (verify-then-edit) — KEEP.** It has a name — artifact evaluation / "Results Reproduced" — and two credible academic Claude-skill codifications. Persist verification outcomes per claim.
4. **Practice 5 (parallel review) — KEEP.** Validated pattern; steal advocate/skeptic pairing and severity tiers.
5. **Practice 2 (syllabus.yaml) — KEEP, lowest risk.** Universal pattern; only migrate if/when the renderer moves to Quarto/JB2, which would absorb it for free.
